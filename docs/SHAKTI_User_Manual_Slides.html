E-Class: Embedded & IoT Microcontroller Core

The E-Class is a 32-bit lightweight embedded processor positioned directly against ARM's Cortex-M series cores, engineered for low power compute, automotive ECUs, smart cards, and industrial motor control.

Microarchitecture Specifications

  • • Pipeline: In-Order 3-stage pipeline (Fetch → Decode/Execute → Writeback).
  • • Clock Speed: Up to 200 MHz on silicon; 50 MHz on Artix-7 FPGA.
  • • ISA Extensions: RV32I / RV32E base with M (Multiplier/Divider), A (Atomic), C (Compressed 16-bit).
  • • Branch Predictor: Optional BHT (Branch History Table) / Return Address Stack (RAS).

3-Stage In-Order Pipeline Flow

S1
Instruction Fetch (IF)
PC generation, Instruction Cache lookup / BRAM access
S2
Decode & Execute (ID / EX)
Register read, ALU ops, branch resolution, multi-stage mul/div
S3
Memory & Writeback (MEM / WB)
Data Cache access, register file commit, CSR updates
Design written in Bluespec SystemVerilog (BSV) for formal verification
Target Market: Automotive sensors, Smart meters, Motor control, Ultra-low-power IoT ARM Cortex-M0+/M3 Competitor

C-Class: Mid-Range 64-Bit Controller Core

The C-Class is a 64-bit industrial-grade core operating up to 1 GHz on silicon, equipped with full MMU (Sv39) support to run standard Linux distributions, targeting mid-range industrial controllers, networking gateways, and storage nodes.

Feature Attribute SHAKTI E-Class SHAKTI C-Class
Word Size (XLEN) 32-bit (RV32) 64-bit (RV64)
Pipeline Stages 3-Stage In-Order 5-Stage In-Order (Fetch, Decode, Exec, Mem, WB)
Silicon Frequency < 200 MHz 800 MHz – 1.0 GHz
Memory Management Unit PMP Only (Physical Memory Protection) Sv39 MMU (Virtual Memory for full Linux OS)
Target ARM Equivalent ARM Cortex-M0+ / M4 ARM Cortex-A35 / Cortex-A55
Operating System Baremetal, FreeRTOS, Zephyr Full Linux, FreeBSD, RTEMS, FreeRTOS
Reference SoC for C-Class: VAJRA (implemented on Artix-7 100T) RV64IMAC + Dual FPU support

The Swadeshi Microprocessor Challenge supports three official SoC implementations targeted at Digilent's Xilinx Artix-7 FPGA development platforms.

Hardware Connections & Dual-Channel FTDI Debugger

The Arty-7 board utilizes a single onboard FTDI FT2232H USB-to-UART/FIFO chip connected to the Micro-USB port (J10). This provides power, hardware JTAG debugging, and serial communication through a single cable.

Single Cable Dual-Channel Routing

Channel A (MPSSE Engine) JTAG Debug

Talks directly to OpenOCD via JTAG (TCK, TMS, TDI, TDO), providing GDB hardware breakpoint and register stepping capability.

Channel B (Serial UART) Console I/O

Wired directly to the SHAKTI SoC UART0 (TX/RX) pins, presenting a standard virtual COM port (`/dev/ttyUSB0` or `COMx` @ 19,200 baud).

Step-by-Step Connection Guide

  1. Connect J10 Port: Plug the Micro-USB cable into connector J10 on the Arty board and connect to your host Linux/Windows PC.
  2. Check Power LED (LD11): Ensure the green power indicator LED lights up, confirming 5V USB bus power delivery.
  3. Verify Linux Device Nodes:
    $ ls -l /dev/ttyUSB*
    /dev/ttyUSB0   (UART Console)
    /dev/ttyUSB1   (OpenOCD JTAG)
No external JTAG pod (like J-Link or Olimex) required for standard debugging! FT2232H Hardware Acceleration

Programming SHAKTI onto Arty-7 SPI Configuration Memory

To make the SHAKTI SoC permanent so it boots instantly whenever power is applied, the compiled .mcs configuration file is flashed into the onboard Quad-SPI Flash memory.

Vivado Hardware Manager Procedure

  1. Open Vivado → Hardware Manager → Open Target → Auto Connect.
  2. Right-click on the FPGA target (xc7a35t or xc7a100t).
  3. Select Add Configuration Memory Device.
  4. Search & select flash part:
    • Manufacturer: Spansion (s25fl128sxxxxxx0) or Micron (n25q128-3.3v)
    • Density: 128 | Type: spi | Width: x1_x2_x4
  5. Browse and select the downloaded pinaka.mcs file.
  6. Click OK / Program to burn the SoC bitstream to flash memory.
Option B: Automated Command Line (SP2020) bash
# 1. Clone SP2020 repo:
git clone https://gitlab.com/shaktiproject/sp2020.git
cd sp2020/e32-a35/
# 2. Build and program MCS in one shot: make generate_verilog generate_boot_files \
    ip_build arty_build generate_mcs \
    program_mcs JOBS=4
⚠️ After flashing, press the board's PROG button (or power cycle) to load the SoC into FPGA fabric!
Prebuilt .mcs files available on Shakti GitLab: sp2020/-/tree/master/mcs Persistent Non-Volatile Boot

SoC Memory Map & Peripheral Addressing

SHAKTI uses a unified Memory-Mapped I/O (MMIO) address space. Device control registers are mapped directly to specific physical address ranges accessed using standard RISC-V load (lw) and store (sw) instructions.

Peripheral Block Base Address Range Description / Functionality Supported Targets
Boot ROM 0x0000_1000 - 0x0001_0FFF Contains first-stage bootloader & logo ASCII art All SoCs
UART 0 0x0001_1300 - 0x0001_1340 Primary console connected to USB FTDI chip (19,200 baud) All SoCs
UART 1 / UART 2 0x0001_1400 / 0x0001_1500 Auxiliary serial channels routed to Arduino headers All SoCs
SPI 0 / SPI 1 0x0002_0000 / 0x0002_0100 SPI Flash & external sensors/SD card interface All SoCs
PWM 0 to 5 0x0003_0000 - 0x0003_05FF 6 independent pulse width modulation channels for motor/LEDs All SoCs
GPIO & PinMux 0x0004_0100 & 0x0004_1500 32 General Purpose I/O pins & dynamic pin multiplexing All SoCs
CLINT (Core Local Interruptor) 0x0200_0000 - 0x020B_FFFF Standard RISC-V timer (mtime/mtimecmp) and software IPI All SoCs
PLIC (Platform-Level Interrupt) 0x0C00_0000 - 0x0C01_001F Routes external peripheral interrupts to processor core All SoCs
Main Memory (BRAM / DDR3) 0x8000_0000 - 0x8FFF_FFFF Pinaka: 128KB BRAM | Parashu: 256MB DDR3 | Vajra: 128MB DDR3 Target Dependent
Unified memory architecture compliant with RISC-V Privileged Architecture v1.10 Standard MMIO Register Layout

Application Lifecycle: Adding & Compiling Code

Applications in SHAKTI-SDK are modular. Small footprint sensor demos and baremetal routines live under software/examples/ with dedicated Makefiles linking against the BSP.

4 Steps to Add an Application

  1. Choose Device Directory: Navigate to ./software/examples/XYZ_applns (where XYZ = uart, gpio, spi, etc.).
  2. Create App Folder: Create a folder, e.g. hello_world/ and write hello_world.c.
  3. Create Local Makefile: Define source files, flags, and link against BSP headers (uart.h).
  4. Register in Master Makefile: Add hello_world to the application list in software/examples/Makefile.
⚡ Build Commands:
# List all registered applications:
make list_applns
# Compile application for Pinaka (RV32): make software PROGRAM=hello_world TARGET=pinaka
# Compile application for Parashu / Vajra: make software PROGRAM=hello_world TARGET=parashu
Build outputs: Generates .elf, disassembly .dump, and memory initialization file.
Target options: TARGET=pinaka, parashu, or vajra Standard GNU Makefile Build System

Interactive Debugging Mode: 3-Terminal Workflow

Debug mode allows developers to dynamically download ELF executables into RAM over JTAG, set hardware breakpoints, inspect memory, and step through instructions using GNU Debugger (GDB).

Terminal 1: UART Terminal

Displays printf output from UART0:

sudo miniterm.py /dev/ttyUSB0 19200
Listens on virtual COM port @ 19,200 baud, 8N1.
Terminal 2: OpenOCD Server

Connects JTAG via FTDI & opens port 3333:

$ cd ./bsp/third_party/artix7_35t
sudo openocd -f ftdi.cfg
Listens for remote GDB connections on port 3333.
Terminal 3: RISC-V GDB

Loads program into RAM & executes:

$ riscv32-unknown-elf-gdb
(gdb) target remote :3333
(gdb) file output/app.elf
(gdb) load
(gdb) continue
Loads in 1-2 seconds; full breakpoint support.
For 64-bit Vajra SoC, replace command with riscv64-unknown-elf-gdb Real-Time Non-Intrusive In-Circuit Emulation
Chapter 5.5 • Deployment Mode Section 5.5 (Page 37-38)

Running in Standalone Mode: Autonomous Power-On Boot

In Standalone Mode, the application no longer requires a host PC or debugger. The binary is stored permanently in Flash memory. On reset, the first-stage BootROM copies the binary from Flash into RAM and begins execution automatically.

Debug Mode vs. Standalone Mode

Debug Mode (Development)

Requires Host PC, OpenOCD, and GDB running. Program resides in volatile RAM and is lost upon power cycle.

Standalone Mode (Production)

Autonomous operation. The binary is written to non-volatile SPI Flash memory. Boots automatically upon power-on or board reset.

🚀 Uploading Application to Flash:
# From shakti-sdk root directory:
cd shakti-sdk
make upload PROGRAM=hello_world TARGET=pinaka
🔄 Hardware Boot Sequence:
  1. Power on / Reset triggered.
  2. Core fetches instructions from BootROM (0x0000_1000).
  3. BootROM reads user application from SPI Flash (0x0002_0000).
  4. Payload copied to RAM (0x8000_0000).
  5. Core jumps to RAM and launches user application.
Tip: Always debug in RAM first; flash to Standalone once verified!
Integrated uploader tool packages and flashes binary automatically Fully Autonomous Production Boot

Arduino Pin Mapping & Dynamic PinMux Architecture

The Arty-7 board maps SHAKTI pins to standard Arduino Uno Rev3 headers and Digilent PMOD connectors. The PinMux register dynamically switches physical pins between GPIO, UART, PWM, and SPI functions at runtime.

PinMux Register (Base: 0x0004_1500)

Every device pin is controlled by a 2-bit pair in the PinMux configuration register:

Bits = '00' Default: GPIO Mode
Bits = '01' UART1 / UART2 / SPI1 Mode
Bits = '10' PWM Output (PWM0 to PWM5)
Bits = '11' Reserved / Undefined
💻 Configuring PinMux in C:
// Enable PWM0 on CK_IO[3] (set bits 7:6 to '10'):
volatile uint32_t *pinmux = (uint32_t *)0x00041500;
*pinmux |= (0b10 << 6);
// Enable UART2 TX on CK_IO[3] (set bits 7:6 to '01'): *pinmux &= ~(0b11 << 6);
*pinmux |= (0b01 << 6);
Full Arduino compatibility enables reuse of hundreds of off-the-shelf sensor shields!
